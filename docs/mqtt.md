# MQTT で測位結果を送る

本体は、自分の MQTT ブローカー(Mosquitto など)へ、設定の間隔ごとに1回、最新の測位結果を SenML(RFC 8428、JSON)で送れます。ここでは、設定のしかた、送られる内容、届いていることの確かめ方、うまくいかないときの見かたをまとめます。

## 用意するもの

- MQTT ブローカー。Mosquitto 2.x で確認しています。ユーザー名とパスワードで認証し、TLS(通常はポート 8883)で暗号化するのが標準の使い方です。
- TLS を使うときは、ブローカーのサーバ証明書を検証するための CA 証明書(PEM)。自分で CA を作っているときはその CA、Let's Encrypt など公開の CA で発行しているときは不要です(本体に内蔵の公開 CA の一覧で検証します)。
- 本体が Wi-Fi でブローカーに届くこと。

TLS の証明書は、本体が接続に使うホスト名(または IP アドレス)が証明書の名前(SAN)と一致している必要があります。IP アドレスで接続するときは、証明書の SAN に IP アドレスが **DNS 名としても** 入っていないと検証に通りません(本体の TLS ライブラリの仕様)。ホスト名で接続するのが無難です。

## 設定

設定は、本体の SD カードの設定ファイル(`/m5f9p/m5f9p.yaml`)の `mqtt` の節に書きます。アプリの「設定」→「本体の設定を編集」→「MQTT 配信」からも書けます。どちらも再起動なしで反映します。

```yaml
mqtt:
  enable: true
  host: "broker.example.jp"   # ブローカーのホスト名か IP アドレス
  port: 8883                  # TLS なら 8883、平文なら 1883 が一般的
  tls: true
  ca: "/m5f9p/mqtt_ca.pem"    # CA 証明書(PEM)。SD カードのパスか、PEM そのもの。空なら内蔵の公開 CA の一覧で検証
  user: "rover"
  password: "..."             # 本体が暗号化して書き直す
  clientId: ""                # 空なら受信機名
  topic: ""                   # 空なら m5f9p/<受信機名>/fix
  interval: 10                # 送る間隔(秒)。1〜3600
  retain: false               # true にすると、最後の位置をブローカーが保持する(あとから購読した側にもすぐ届く)
```

| 項目 | 内容 |
|---|---|
| `ca` | SD カードのパス(`/m5f9p/mqtt_ca.pem` など)を書くか、PEM の中身(`-----BEGIN CERTIFICATE-----` で始まる文字列)をそのまま書きます。アプリの編集画面では PEM を貼り付けられます。空欄なら、本体に内蔵の公開 CA の一覧で検証します |
| `clientId`、`topic` | 空欄なら受信機名(`receiver.name`)から作ります。受信機名に空白など MQTT や SenML に使えない文字があるときは `-` に置き換えます |
| `retain` | ダッシュボードなどで「最後の位置」をすぐ出したいときに有効にします |

パスワードは、本体が設定ファイルを書くときに暗号化します。アプリの `config.get` ではパスワードを返しません(設定済みかどうかだけ分かります)。

### 入・切

次のどれでも切り替えられ、どれも設定ファイルの `mqtt.enable` を書き換えます。

- 本体の Setup の `MQTT: On` / `MQTT: Off` のタイル(ブローカー `host` を設定しているときだけ出ます)
- アプリの「設定」→「接続の設定」→「MQTT で測位結果を送る」→「変更する」
- コマンド `run.set {"mqtt":true}`(`mise run cmd '{"cmd":"run.set","mqtt":true}'`)

## 送られる内容

設定の間隔ごとに1回、そのとき最新の測位結果(測位できているときだけ)を、1つの SenML パック(JSON の配列)として QoS 0 で publish します。大きさは約 430 バイトです。

```json
[{"bn":"m5f9p:","bt":1760000000.2,"n":"lat","u":"lat","v":35.691257617},
 {"n":"lon","u":"lon","v":139.770043408},
 {"n":"alt","u":"m","v":26.523},
 {"n":"hae","u":"m","v":63.346},
 {"n":"hacc","u":"m","v":0.014},
 {"n":"vacc","u":"m","v":0.022},
 {"n":"fix","v":4},
 {"n":"sats","u":"count","v":31},
 {"n":"speed","u":"m/s","v":0.00},
 {"n":"heading","u":"deg","v":123.4}]
```

| 名前 | 単位 | 内容 |
|---|---|---|
| `bn` | | 名前の共通部分。クライアント ID と `:`。各レコードの名前は `bn` + `n`(例 `m5f9p:lat`) |
| `bt` | 秒 | 測位の時刻(UTC、1970 年からの秒数。小数 1 桁) |
| `lat`、`lon` | `lat`、`lon` | 緯度、経度(度。小数 9 桁) |
| `alt` | `m` | 標高(楕円体高からジオイド高を引いた値。SD カードにジオイドモデルがあればその値、なければ F9P 内蔵のジオイド) |
| `hae` | `m` | 楕円体高 |
| `hacc`、`vacc` | `m` | 推定精度(水平、垂直) |
| `fix` | | 測位の状態。NMEA の quality と同じ(1:単独 4:Fix 5:Float 6:推測航法) |
| `sats` | `count` | 使っている衛星の数 |
| `speed` | `m/s` | 速度 |
| `heading` | `deg` | 進行方向(北が 0、時計回り)。速度 0.5 m/s 以上のときだけ付きます(止まっている間は当てにならないため) |

単位は IANA の SenML Units 登録簿にあるものです(`deg` は RFC 8798 で追加されたもの)。

## 届いていることを確かめる

### ブローカーで購読する

PC で購読するのがいちばん確実です。Mosquitto のクライアント(`mosquitto_sub`)を使う例です。

```bash
# TLS(自分の CA で検証)
mosquitto_sub -h broker.example.jp -p 8883 --cafile ca.pem -u rover -P '...' -t 'm5f9p/#' -v

# TLS なし
mosquitto_sub -h 192.168.0.10 -p 1883 -u rover -P '...' -t 'm5f9p/#' -v
```

`-v` でトピックも出ます。受信時刻も付けるときは `-F '%I %t %p'` を足します。設定の間隔ごとに、上の形の JSON が 1 行ずつ流れます。

### アプリで見る

Windows、Android とも「状況」のタブの「本体」の枠に `MQTT` の行があります。

| 表示 | 意味 |
|---|---|
| `接続中(n 件送信)` | ブローカーにつながっていて、起動してから n 件送った |
| `Wi-Fi の接続待ち` | Wi-Fi につながっていない |
| `測位待ち(時計合わせ)` | TLS の証明書の検証に時計が要るため、測位の時刻で時計を合わせるのを待っている。測位ができると進む |
| `再接続待ち(エラー n 回)` | 接続か送信に失敗して、次の試行を待っている。間隔は 5 秒から倍々に増え、最長 5 分 |
| `接続しています` | 接続の途中 |

### 本体のログで見る

USB をつないでシリアルログを読むと、原因まで分かります(`mise run usb-attach` のあと `mise run log 30`)。

- 10 秒ごとの `STAT` 行の `mqtt(st=5 pub=102 err=0)`。`st` は状態(0:使わない 1:Wi-Fi 待ち 2:時計待ち 3:再試行待ち 4:接続中 5:接続済み)、`pub` は送った数、`err` は失敗の数。
- つながったとき: `MQTT: connected broker:8883 TLS heap 65188 -> 16700 (48488 used)`。`heap` は内蔵 RAM の空きで、接続で使った量が分かります。
- 失敗したとき: `MQTT: connect failed broker:8883 state=-2 tls=X509 - Certificate verification failed ...`。`state` は MQTT クライアント(PubSubClient)の値、`tls=` は TLS ライブラリのメッセージです。

| `state` | 意味 |
|---|---|
| -4 | 応答がなくタイムアウト |
| -2 | 接続できない(届かない、ポートが違う、TLS の検証に失敗) |
| 4 | ユーザー名かパスワードが違う |
| 5 | 許可されていない(ブローカーの ACL など) |

コマンド `mise run cmd '{"cmd":"status"}'` の応答の `mqtt` にも同じ内容が入ります(MQTT を有効にしているときだけ)。

## うまくいかないとき

| 症状 | 見るところ |
|---|---|
| `state=-2` で `tls=` が出ない | TCP の時点で届いていません。ホスト、ポート、ファイアウォールを確かめます。開発機の WSL2(ミラーモード)でブローカーを動かしているときは、Windows の Hyper-V ファイアウォールが WSL への着信を遮断します(DEVELOPE.md の「MQTT で測位結果を送る」を参照) |
| `tls=X509 - Certificate verification failed` | CA が違う、または接続に使った名前が証明書の名前と合っていません(IP アドレスで接続しているときは上の注意を参照) |
| `測位待ち(時計合わせ)` のまま | 屋内などで測位ができていません。TLS なしなら時計は不要です |
| `state=4` / `state=5` | ユーザー名、パスワード、ブローカー側の権限 |
| つながるが本体の動作が不安定、再起動する | 内蔵 RAM の不足。下の「内蔵 RAM」を参照 |

## 内蔵 RAM(TLS を使うときの注意)

TLS は、接続している間、本体の内蔵 RAM を約 48KB 使います(TLS ライブラリの送受信バッファなど。本体のビルド構成では変えられません)。BLE を使っていると内蔵 RAM の空きは約 65KB なので、TLS で接続すると残りが約 16KB になり、ほかの処理に支障が出るおそれがあります。

| 構成 | 内蔵 RAM の空き |
|---|---|
| BLE あり、MQTT なし | 約 65KB |
| BLE あり、TLS で接続中 | 約 16KB |
| BLE なし(`ble.enable: false`)、MQTT なし | 約 135KB |

次のどちらかを勧めます。

- TLS を使うときは BLE を切る(設定ファイルの `ble.enable: false`。アプリは USB で接続します)
- BLE を使い続けるときは TLS なし(`tls: false`、ポート 1883)にして、LAN や VPN の中だけで送る

TLS なしの MQTT が使う内蔵 RAM は数 KB です。測定の詳細は [DEVELOPE.md](../DEVELOPE.md) の「MQTT で測位結果を送る」にあります。
